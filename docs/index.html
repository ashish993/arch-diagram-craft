01 / Review

Clarify what changes the diagram

Review your request and sources first. If a missing choice could change scope, audience, or meaning, ask up to three focused questions.

02 / Plan

Agree the useful view

Summarize the view, evidence, scope, output, and assumptions. Optional unknowns stay labeled; they do not block a useful draft.

03 / Build + inspect

Make and review the diagram

When you ask for a diagram, the agent proceeds after the short plan, then checks legibility, arrowheads, boundaries, and overlaps.

Start with a prompt

Copy a prompt into your AI tool, replace the bracketed details, and attach the requirements or code it should use. The clarification-first prompt is for broad requests; the others are ready-made diagram tasks.

Start with a vague request

Use the arch-diagram-craft skill to help me create a diagram for [system or process]. First review what I have provided. If any missing detail could change the diagram's purpose, scope, audience, or meaning, ask me up to three focused questions before drawing. After I answer, summarize the selected diagram view, evidence, scope, deliverables, and remaining assumptions in a short plan, then create it. If a detail is not critical, mark it as an assumption and keep going. Render and visually inspect the result, fix and re-render defects, and include an evidence note.

AWS three-tier architecture

Use the arch-diagram-craft skill to create an AWS three-tier architecture diagram for [application/use case].

Users: [user types and entry points]
Web tier: [hosting and static-content requirements]
Application tier: [runtime, APIs, scaling requirements]
Data tier: [database, storage, backup and recovery requirements]
Region and availability: [region, AZ count, uptime or recovery targets]
Security and network: [identity, public/private subnets, ingress/egress, trust boundaries]
Constraints: [budget, existing services, compliance, or services to avoid]

Use only the AWS services and facts I provide. Mark proposed services or unspecified choices as assumptions. Show account/region boundaries, network zones, tier placement, and labeled traffic arrows. Save editable HTML/SVG and an evidence note. Render and inspect every label, arrow endpoint, crossing, spacing, and overlap at desktop and mobile sizes. Fix and re-render defects; list open design questions.

System context and containers

Use the arch-diagram-craft skill to create a system context and container diagram for [system]. Audience: [audience]. Use these requirements, architecture notes, and source files: [paste or link them]. Show users, the system boundary, neighboring systems, major applications/services/data stores, and labeled relationships. Separate facts from assumptions and unknowns; include an evidence map. Save editable HTML/SVG, render it, and fix unreadable text, incorrect arrows, clipped content, or overlaps before delivery.

Component diagram from code

Use the arch-diagram-craft skill to inspect this repository and create a component diagram for [service/module/path]. Trace responsibilities and dependencies from source code, interfaces, call sites, and tests; do not infer components from folder names alone. Show supported relationships and label uncertain boundaries. Include an evidence map with file references. Save editable HTML/SVG, render it, and correct and re-render text, arrow, spacing, or overlap defects.

Trust-boundary data flow

Use the arch-diagram-craft skill to diagram [data/process] across its trust boundaries. Show actors, systems, data stores, boundary zones, and each data flow with direction and a concise label. Mark sensitive data and crossings only when supported by the evidence; list unknown controls rather than assuming them. Sources: [paste or link requirements/code]. Save editable HTML/SVG and an evidence map. Render and inspect arrow endpoints, labels, boundary crossings, readability, and spacing; fix and re-render defects.

Sequence diagram

Use the arch-diagram-craft skill to create a sequence diagram for [user or system interaction]. Use these steps and source materials: [describe steps or link code/API docs]. Show participants, calls, responses, asynchronous events, and relevant failure or timeout branches in order. Do not invent unspecified behavior; mark gaps as open questions. Save editable HTML/SVG with an evidence note, render it, and fix incorrect message direction, hidden text, or overlap before delivery.

Business flowchart

Use the arch-diagram-craft skill to create a business flowchart for [process]. Audience: [business roles]. Start with [trigger], include [decisions, handoffs, exception/recovery paths], and end with possible outcomes. Use plain language and show who performs each step. Base the flow on: [paste process notes]. Mark uncertain steps for confirmation. Save editable HTML/SVG, render it, verify decision branches, arrow direction, readable text, and spacing, and correct and re-render any defects.

A plan is a concise summary before work, not an extra approval gate. You can ask for review or planning only when you want the agent to stop before creating the diagram. A prompt can guide a reviewed draft; it cannot establish that an architecture is correct or production-ready.

A diagram should answer more than “what connects?”

  • 01Which source statement supports each important component and flow?
  • 02Where does data cross a trust boundary, and in which direction?
  • 03Can a reader follow every arrow to its intended endpoint?
  • 04Are assumptions and missing details visible instead of quietly invented?
